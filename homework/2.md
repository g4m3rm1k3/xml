#### 1. Concept: What Is Testing & Types
- **Unit Testing (Our Focus)**: Test small, isolated pieces (e.g., a function like `parse_gcode`). Input → Expected Output. Fast, runs in seconds.
- **Integration Testing**: Test how pieces interact (e.g., parser + simulator). Slower, but catches wiring issues.
- **End-to-End (E2E)**: Test whole app (e.g., GUI input → output). Rare for us now—use for full flows later.
- **Other Flavors**: Regression (prevent old bugs), Smoke (basic "does it run?"), Performance (speed).

**What Do We Test For?**
- **Correctness**: Does it do what the BRD says? (E.g., parse "G1 X10" → correct commands.)
- **Edge Cases**: Weird inputs (e.g., empty code, negative values, malformed G-code).
- **Error Handling**: Does it fail gracefully? (E.g., raise exception on invalid command, not crash.)
- **Invariants**: Unbreakable rules from DDD (e.g., positions always floats, modals persist).
- **Not Everything**: Skip trivial getters/setters; focus 80% on core logic. "Test behaviors, not implementation" — if refactor changes internals, tests still pass.

Rationale: Tests are your safety net. In real jobs (e.g., CNC software), untested code risks machine crashes. They also document: A test shows "how this should work."

#### 2. How to Understand Code Before Testing
Don't test blind—prep like a detective. This step is 50% of good testing.

- **Step 1: Read & Map**: Skim module (e.g., `parser.py`). Identify:
  - Inputs: What goes in? (E.g., `parse_gcode(text: str)` → string.)
  - Outputs: What comes out? (List of GCodeLine.)
  - Side Effects: Changes state? (Parser: None, pure function.)
  - Dependencies: Imports what? (re for regex.)
- **Step 2: Trace Flow**: Run mentally or with debugger. E.g., For parser: "Input 'G1 X10' → regex matches → build commands → return lines."
- **Step 3: Ask Questions**:
  - Happy Path: Normal input (e.g., valid G-code).
  - Sad Paths: Bad input (e.g., "GABC" → should raise? Or skip?)
  - Boundaries: Min/max (e.g., float precision, long lines).
- **Step 4: Use Tools**: 
  - Print/debug: Add temporary `print`s to see intermediates.
  - Type Hints: Yours have them (e.g., `List[GCodeLine]`)—use mypy to check.
  - Docs/Comments: If missing, add as you go.

Practice Tip: For your `services.py`, trace `execute_line`: Input state/line → process commands → update position/toolpath. Note: Mutates state (side effect) → Test by checking state after.

This understanding prevents "over-testing" (e.g., don't test regex internals if it works).

#### 3. How Tests Work: Mechanics
Tests are code that runs your code. `pytest` finds files like `test_*.py`, runs functions starting with `test_`.

- **Basic Structure**: 
  ```python
  def test_function_name():
      # Code here
      assert something == expected  # If false, test fails
  ```
- **Run**: `pytest` (or `pytest -v` for verbose). Green = pass; Red = fail with details.

- **Arrange-Act-Assert (AAA) Pattern**: Your key framework—organizes tests like a story.
  - **Arrange**: Setup (inputs, mocks). E.g., create sample code string.
  - **Act**: Call the thing (e.g., `lines = parse_gcode(code)`).
  - **Assert**: Check results (e.g., `assert len(lines) == 1`).
  Why? Readable, debuggable. Without AAA, tests become messy "spaghetti asserts."

  Example (from homework stub):
  ```python
  def test_parse_simple_move():
      # Arrange
      code = "G1 X10.0 Y20.5"
      
      # Act
      lines = parse_gcode(code)
      
      # Assert
      assert len(lines) == 1
      assert lines[0].commands[0] == GCodeCommand("G", 1.0)
  ```

- **Fixtures**: Reusable setup code (like test helpers). Avoid duplication.
  - Define: `@pytest.fixture def name(): return setup`
  - Use: Pass as arg to test (e.g., `def test_x(fixture_name):`).
  - Why? For shared state (e.g., a default MachineState for multiple tests).
  - Scope: Default per-test; use `@pytest.fixture(scope="module")` for once-per-file.

  Example:
  ```python
  import pytest
  from src.domain import MachineState

  @pytest.fixture
  def default_state():
      return MachineState()  # Reusable empty state
  ```

  Pitfall: Don't mutate fixtures across tests—pytest isolates them.

- **Assertions & Matchers**: `assert x == y` basic; for floats, `assert math.isclose(x, y)`. Pytest rewrites for better errors (e.g., shows diffs).

- **Mocking (Advanced, Skip for Now)**: Fake dependencies (e.g., mock GUI for sim tests). We'll cover later.

#### 4. Best Practices: Actual Hands-On Tips
- **Test Pyramid**: 70% units (fast), 20% integration, 10% E2E (slow).
- **Coverage**: Aim 80%+ (use `pytest --cov`). But quality > quantity—test critical paths.
- **TDD Flow**: Write failing test first (red), make it pass (green), refactor. Builds confidence.
- **Naming**: Descriptive, e.g., `test_parse_with_invalid_code_raises_error`.
- **Edge Cases to Always Test**:
  - Null/empty inputs.
  - Max/min values (e.g., huge floats).
  - Errors (use `with pytest.raises(ValueError):`).
- **CI/CD Tie-In**: In real work, tests run automatically (e.g., GitHub Actions). For you: Run before commits.
- **Common Mistakes**: Over-mocking (tests pass but app fails); ignoring flakes (intermittent fails).
- **Tools**: VS Code pytest extension—run/debug tests visually.
